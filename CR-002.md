# CR-002 — SurrealDB Edge Taxonomy + Connected Subgraph Selection (Embedded)

## Summary
Implement a **Prune code graph** in **embedded SurrealDB** that supports:

- File-level import graph (module neighborhood)
- File→fragment containment edges (fast “pull relevant fragments from file”)
- Fragment→fragment semantic edges (refs/defs, calls, type uses, JSX uses, test links)
- Connected subgraph extraction for “small, coherent packs” (great for smaller LLMs)

This change request defines:
- the edge taxonomy (types, metadata, weights)
- SurrealQL schema additions (relation tables + indexes)
- graph expansion + connector logic (recursive collection + shortest paths)
- tests + acceptance criteria

---

## Goals
1. Define a stable **edge taxonomy** for multi-language repos (TS/TSX + Swift + Rust).
2. Store edges as first-class **SurrealDB relation tables**.
3. Implement **connected subgraph selection** driven by:
   - seed fragments from retrieval (vector/FTS/hybrid)
   - graph expansion on file graph + fragment graph
   - optional shortest-path “connectors”
4. Keep reverse lookups using Surreal’s reverse traversal (`<-edge<-`) instead of storing separate reverse edges.

---

## Non-goals
- Weighted shortest path (Surreal shortest path is unweighted; weights are used for ranking/pruning)
- Perfect cross-language symbol resolution
- Full call graph for all code paths (start pragmatic)

---

## Data model

### Node tables
- `repo`
- `file`
- `frag`
- (optional) `symbol`

### Relation tables
We use three core relation tables:

1) `imports` — **file → file**  
2) `contains` — **file → frag**  
3) `rel` — **frag → frag** (typed by `etype`)

---

## Edge taxonomy (exact)

### A) File graph edges: `imports` (file → file)
Used for “which files are likely needed together”.

**Edge table:** `imports`  
**Direction:** `IN file OUT file`  
**Fields (edge metadata):**
- `repo_id: string` (required)
- `lang: string` one of `ts|tsx|swift|rust`
- `specifier: string` (original import string)
- `resolved_path: string|null` (repo-relative)
- `is_type_only: bool|null` (TypeScript only)
- `weight: float` (default 1.0)
- `confidence: float` (default 1.0)
- `origin: string` (extractor name, e.g. `ts_import_resolver`)

**When emitted**
- TS/TSX: `import … from …`, `export … from …`
- Swift: `import Module` (coarse)
- Rust: `mod foo;`, `use crate::…` (module-level)

**Default weight rules**
- normal import: `1.0`
- re-export / barrel: `0.8`
- generated/typings: `0.4`

---

### B) Containment edges: `contains` (file → frag)
Supports “pull fragments in a file quickly” and reverse lookup “frag → file”.

**Edge table:** `contains`  
**Direction:** `IN file OUT frag`  
**Fields:**
- `repo_id: string`
- `kind: string` (duplicate of frag.kind for fast filtering)
- `symbol: string|null` (duplicate)
- `start_line: int`, `end_line: int` (optional convenience)
- `weight: float` (default 0.2)
- `confidence: float` (default 1.0)

**When emitted**
- Every fragment produced by indexing creates one contains edge.

**Default weight rules**
- `api_summary`: `0.4`
- exported/public symbol: `0.3`
- private/local symbol: `0.1`

---

### C) Fragment graph edges: `rel` (frag → frag) with `etype`
The “semantic glue” for connected packs.

**Edge table:** `rel`  
**Direction:** `IN frag OUT frag`  
**Fields:**
- `repo_id: string`
- `etype: string` (required)
- `weight: float`
- `confidence: float`
- `origin: string`
- `meta: object` (freeform)

**Allowed `etype` values (v1)**
- `ref_def` — reference fragment → definition fragment  
- `calls` — callsite fragment → callee fragment  
- `type_uses` — fragment → type definition fragment  
- `jsx_uses` — TSX fragment → component definition fragment  
- `tests` — test fragment → implementation fragment (heuristic)

**Default weight rules**
- `ref_def`: 1.0
- `calls`: 0.9
- `type_uses`: 0.7
- `jsx_uses`: 0.8
- `tests`: 0.5

> Reverse traversal is done via `<-rel<-` (no stored reverse edges).

## SurrealDB schema changes (SurrealQL)

### Create file: `crates/ce-store-surreal/schema/prune_edges.surql`

```sql
DEFINE TABLE imports  SCHEMALESS TYPE RELATION IN file OUT file;
DEFINE TABLE contains SCHEMALESS TYPE RELATION IN file OUT frag;
DEFINE TABLE rel      SCHEMALESS TYPE RELATION IN frag OUT frag;

-- Indexes for fast expansion by repo + direction
DEFINE INDEX imports_repo_in   ON TABLE imports  FIELDS repo_id, in;
DEFINE INDEX imports_repo_out  ON TABLE imports  FIELDS repo_id, out;
DEFINE INDEX imports_repo_lang ON TABLE imports  FIELDS repo_id, lang;

DEFINE INDEX contains_repo_in   ON TABLE contains FIELDS repo_id, in;
DEFINE INDEX contains_repo_out  ON TABLE contains FIELDS repo_id, out;
DEFINE INDEX contains_repo_kind ON TABLE contains FIELDS repo_id, kind;

DEFINE INDEX rel_repo_in    ON TABLE rel FIELDS repo_id, in;
DEFINE INDEX rel_repo_out   ON TABLE rel FIELDS repo_id, out;
DEFINE INDEX rel_repo_etype ON TABLE rel FIELDS repo_id, etype;
```

### Apply during schema install
Update schema installer to also apply `prune_edges.surql`.

## Write-path changes (edge creation)

### Imports edge example
```sql
RELATE file:src_main->imports->file:src_app
SET repo_id = $repo_id,
    lang = "tsx",
    specifier = "./App",
    resolved_path = "src/App.tsx",
    weight = 1.0,
    confidence = 1.0,
    origin = "ts_import_resolver";
```

### Contains edge example
```sql
RELATE file:src_app->contains->frag:frag123
SET repo_id = $repo_id,
    kind = "api_summary",
    symbol = NONE,
    start_line = 1,
    end_line = 42,
    weight = 0.4,
    confidence = 1.0;
```

### Rel edge example
```sql
RELATE frag:fragA->rel->frag:fragB
SET repo_id = $repo_id,
    etype = "ref_def",
    weight = 1.0,
    confidence = 0.9,
    origin = "ref_def_matcher",
    meta = { ref: "Foo", kind: "identifier" };
```

## Connected subgraph selection algorithm

We build a connected pack in **three phases**:

### Phase 1 — Seeds
Seeds come from retrieval (vector/FTS/hybrid) as a set of fragment record IDs.

### Phase 2 — File neighborhood
For each seed fragment:
1) find parent file via reverse traversal:
```sql
SELECT VALUE <-contains<-file FROM frag:$seed;
```

2) collect a bounded file neighborhood:
```sql
RETURN file:$f.{..2+collect}(->imports[WHERE repo_id = $repo_id]->file);
```

Output: candidate files.

### Phase 3 — Fragment neighborhood + connectors
3A) From candidate files, pull key fragments (prefer summaries/signatures):
- `api_summary`, exported/public definitions, selected types/interfaces

3B) Collect fragment neighborhood around each seed:
```sql
RETURN frag:$seed.{..2+collect}(
  ->rel[WHERE repo_id = $repo_id AND etype INSIDE $etypes]->frag
);
```

3C) If the result is disconnected:
- connect top seeds to a chosen hub with unweighted shortest path:
```sql
RETURN frag:$seed.{..4+shortest=frag:$hub+inclusive}(
  ->rel[WHERE repo_id = $repo_id AND etype INSIDE $etypes]->frag
);
```

Finally:
- rank/prune fragments down to token budget using:
  - hop distance decay
  - edge weight decay
  - kind priority (`api_summary` > signatures/types > slices > bodies)

## Tests

### T1 — Traversal works both directions
- create file A and B
- `RELATE file:A->imports->file:B`
- assert:
  - `SELECT ->imports->file FROM file:A` includes B
  - `SELECT <-imports<-file FROM file:B` includes A

### T2 — `+collect` bounded neighborhood
- A imports B imports C
- `file:A.{..2+collect}(->imports[WHERE repo_id="r"]->file)` returns B and C

### T3 — `+shortest` connectors
- create a graph with two components and a bridging path
- verify shortest path returns the bridging nodes with `+inclusive`

### T4 — “pack connectivity smoke test”
- create:
  - two fragments in different files
  - edges linking them through imports and rel
- pack should return a connected set under cap

---

## Acceptance Criteria
- Edge schema installs and is idempotent.
- Indexer writes:
  - `imports` edges (file→file)
  - `contains` edges (file→frag)
  - `rel` edges with `etype`
- Connected subgraph selection returns a connected (or nearly connected) set around seeds.
- Reverse traversal uses `<-edge<-` and no reverse edges are stored.

---

## Notes
- Keep edge extraction pragmatic and incremental:
  - start with imports + contains + ref_def
  - add jsx_uses/type_uses/tests after initial correctness is stable
- Prefer strict caps and graceful degradation to avoid runaway graph expansion.
