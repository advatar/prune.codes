# Change Request: SurrealDB Edge Taxonomy + Connected Subgraph Selection (Embedded)

## Summary
Implement a **Prune code graph** in embedded SurrealDB using:

- `RELATE` graph edges (with metadata fields on edges).  [oai_citation:0‡SurrealDB](https://surrealdb.com/docs/surrealql/statements/relate?utm_source=chatgpt.com)  
- Arrow traversal `->edge->record` and reverse traversal `<-edge<-record`.  [oai_citation:1‡SurrealDB](https://surrealdb.com/docs/surrealdb/models/graph?utm_source=chatgpt.com)  
- **Recursive traversal** with `{..+collect}` (collect unique nodes) and `{..+shortest=...}` (shortest path) for connected subgraph extraction.  [oai_citation:2‡SurrealDB](https://surrealdb.com/docs/surrealql/datamodel/idioms)  
- Traversal edge filtering using `->edge[WHERE ...]` patterns.  [oai_citation:3‡SurrealDB](https://surrealdb.com/blog/ten-tips-and-tricks-for-your-surrealdb-queries?utm_source=chatgpt.com)  

The goal is to let Prune build **small, connected context packs** for weaker models by selecting a minimal, relevant subgraph around retrieved seed fragments.

---

## Goals
1. Define a stable **edge taxonomy** for multi-language repos (TS/TSX + Swift + Rust).
2. Store edges as first-class **SurrealDB relation tables** (`TYPE RELATION IN … OUT …`).  [oai_citation:4‡SurrealDB](https://surrealdb.com/docs/surrealql/statements/define/table)  
3. Implement **connected subgraph selection** driven by:
   - seed fragments from retrieval
   - graph expansion in file-graph + fragment-graph
   - optional shortest-path “connectors”
4. Keep edge creation **one-directional** (no duplicated reverse edges); reverse traversal uses `<-edge<-`.  [oai_citation:5‡SurrealDB](https://surrealdb.com/docs/surrealdb/models/graph?utm_source=chatgpt.com)  

---

## Non-goals
- Weighted shortest path (Surreal built-in `+shortest` is unweighted)
- Perfect semantic resolution of symbols across languages
- Full call graph across the repo (we start with pragmatic edges)

---

## Data model

### Node tables (existing / to be ensured)
- `repo`
- `file`
- `frag`

### Relation tables (new)
We will add three core relation tables:

1) `imports` — file → file  
2) `contains` — file → frag  
3) `rel` — frag → frag (typed by `etype`)  

These are defined with Surreal’s relation table type clause.  [oai_citation:6‡SurrealDB](https://surrealdb.com/docs/surrealql/statements/define/table)

## Edge taxonomy (exact)

### A) File graph edges: `imports` (file → file)
Used for “which files are likely needed together”.

**Edge table:** `imports`  
**In/Out:** `IN file OUT file`  
**Fields (edge metadata):**
- `repo_id: string` (required)
- `lang: string` one of `ts|tsx|swift|rust`
- `specifier: string` (original import text)
- `resolved_path: string|null` (repo-relative)
- `is_type_only: bool|null` (TS)
- `weight: float` (default 1.0)
- `confidence: float` (default 1.0)
- `origin: string` (extractor name, e.g. `ts_import_resolver`)

**When emitted**
- TS/TSX: static `import … from …`, `export … from …`
- Swift: `import Module` (module edges are coarse; still useful)
- Rust: `mod foo;`, `use crate::…` (module-level)

**Default weight rules**
- normal import: `1.0`
- re-export / barrel files: `0.8`
- generated/typings: `0.4`

---

### B) Containment edges: `contains` (file → frag)
This supports “pull the right fragments from the right files”.

**Edge table:** `contains`  
**In/Out:** `IN file OUT frag`  
**Fields:**
- `repo_id: string`
- `kind: string` (duplicate of frag.kind for fast filtering)
- `symbol: string|null` (duplicate)
- `start_line: int`, `end_line: int` (optional convenience)
- `weight: float` (default 0.2)
- `confidence: float` (default 1.0)

**When emitted**
- Every fragment created by the indexer creates one `contains` edge.

**Default weight rules**
- `api_summary`: `0.4`
- `exported symbol`: `0.3`
- `private symbol`: `0.1`

---

### C) Fragment graph edges: `rel` (frag → frag) with `etype`
This is the “semantic glue” that makes packs connected.

**Edge table:** `rel`  
**In/Out:** `IN frag OUT frag`  
**Fields:**
- `repo_id: string`
- `etype: string` (required; see below)
- `weight: float`
- `confidence: float`
- `origin: string`
- `meta: object` (freeform; e.g. `{"ref":"Foo","kind":"call"}`)

**Allowed `etype` values (v1)**
- `ref_def` — reference fragment → definition fragment  
- `calls` — callsite fragment → callee fragment  
- `type_uses` — fragment → type definition fragment  
- `jsx_uses` — TSX fragment/file → component definition fragment  
- `tests` — test fragment → implementation fragment (heuristic)  

**Default weight rules**
- `ref_def`: 1.0
- `calls`: 0.9
- `type_uses`: 0.7
- `jsx_uses`: 0.8
- `tests`: 0.5

> Why no reverse edges? Surreal traversal supports reverse lookups with `<-rel<-frag`.  [oai_citation:7‡SurrealDB](https://surrealdb.com/docs/surrealdb/models/graph?utm_source=chatgpt.com)

## Write-path changes (creating edges)

### Use `RELATE … SET …` for edge metadata
Surreal edges can store metadata via `SET` and have required `in/out` fields.  [oai_citation:10‡SurrealDB](https://surrealdb.com/docs/surrealql/statements/relate?utm_source=chatgpt.com)  

#### Imports edge creation (example)
```sql
RELATE file:src_main->imports->file:src_app
SET repo_id = $repo_id,
    lang = "tsx",
    specifier = "./App",
    resolved_path = "src/App.tsx",
    weight = 1.0,
    confidence = 1.0,
    origin = "ts_import_resolver";
```

#### Contains edge creation (example)
```sql
RELATE file:src_app->contains->frag:frag123
SET repo_id = $repo_id,
    kind = "api_summary",
    symbol = null,
    start_line = 1,
    end_line = 42,
    weight = 0.4,
    confidence = 1.0;
```

#### Rel edge creation (example)
```sql
RELATE frag:fragA->rel->frag:fragB
SET repo_id = $repo_id,
    etype = "ref_def",
    weight = 1.0,
    confidence = 0.9,
    origin = "ref_def_matcher",
    meta = { ref: "Foo", kind: "identifier" };
```

### Optional perf optimization (batch insert)
If write throughput is a concern, Surreal supports `INSERT RELATION INTO …` for multiple relations in one statement.  [oai_citation:11‡SurrealDB](https://surrealdb.com/blog/building-real-time-ai-pipelines-in-surrealdb?utm_source=chatgpt.com)  
(Keep as optional; start with `RELATE` batching in Rust first.)

## Connected subgraph selection (how we’ll do it)

We do it in **three phases**:

### Phase 1: Start from retrieved seed fragments
Seeds come from vector/FTS/hybrid retrieval (already part of store).

You have a list:
- `seed_frags: Vec<frag_id>`

### Phase 2: Build the file neighborhood (imports graph)
1) For each seed fragment, find its parent file via reverse traversal:
```sql
SELECT VALUE <-contains<-file FROM frag:$seed;
```
Reverse traversal uses `<-edge<-`.  [oai_citation:12‡SurrealDB](https://surrealdb.com/docs/surrealdb/models/graph?utm_source=chatgpt.com)  

2) For each parent file, collect a bounded import neighborhood using recursive `+collect`:
```sql
file:$f.{..2+collect}(->imports[WHERE repo_id = $repo_id]->file)
```

Recursive traversal with `{..+collect}` collects unique nodes walked.  [oai_citation:13‡SurrealDB](https://surrealdb.com/docs/surrealql/datamodel/idioms)  
Traversal filters like `->imports[WHERE ...]` are supported (pattern shown in docs/blog).  [oai_citation:14‡SurrealDB](https://surrealdb.com/blog/ten-tips-and-tricks-for-your-surrealdb-queries?utm_source=chatgpt.com)  

**Output:** `candidate_files`

### Phase 3: Expand in fragment graph + connect components
3A) Pull key fragments from selected files (cheap, deterministic):
- Always include `api_summary` fragments in those files (if present)
- Include exported/public symbols (if your language pack marks them)

Example query:
```sql
SELECT * FROM frag
WHERE repo_id = $repo_id
  AND file_id INSIDE $file_ids
  AND kind INSIDE ["api_summary", "export", "public"];
```

3B) Expand around seed fragments in `rel` graph:
```sql
frag:$seed.{..2+collect}(
  ->rel[WHERE repo_id = $repo_id AND etype INSIDE $etypes]->frag
)
```

3C) Optional: “connectors” using shortest path
If your expanded set is still disconnected, connect top N seeds to a hub using `+shortest`:

```sql
frag:$seed.{..+shortest=frag:$hub+inclusive}(
  ->rel[WHERE repo_id = $repo_id AND etype INSIDE $etypes]->frag
)
```

SurrealDB supports `{..+shortest=record:id}` and `+inclusive`.  [oai_citation:15‡SurrealDB](https://surrealdb.com/docs/surrealql/datamodel/idioms)  

**Important note:** `+shortest` is unweighted; we’ll use weights later only for ranking/pruning.

## Rust implementation (actual code to add)

### 1) Query helpers (ce-store-surreal)
Create: `crates/ce-store-surreal/src/graph.rs`

```rust
use anyhow::Context;
use serde::Deserialize;
use surrealdb::{Surreal, engine::any::Any};

#[derive(Clone, Debug)]
pub struct GraphParams {
    pub repo_id: String,
    pub max_hops: u32,        // e.g. 2
    pub max_nodes: usize,     // safety cap post-collect
    pub etypes: Vec<String>,  // for rel graph
}

#[derive(Deserialize)]
struct IdRow { id: String }

fn rid(table: &str, id: &str) -> String {
    if id.starts_with(&format!("{table}:")) { id.to_string() }
    else { format!("{table}:{id}") }
}

/// Collect unique nodes reachable within hops using Surreal recursive +collect.
/// The repeated path must return record IDs (or arrays of record IDs).  [oai_citation:16‡SurrealDB](https://surrealdb.com/docs/surrealql/datamodel/idioms)
pub async fn collect_file_neighborhood(
    db: &Surreal<Any>,
    repo_id: &str,
    file_rid: &str,
    max_hops: u32,
) -> anyhow::Result<Vec<String>> {
    let sql = r#"
        LET $repo = $repo_id;
        LET $f = $file;
        RETURN $f.{..$hops+collect}(->imports[WHERE repo_id = $repo]->file);
    "#;

    let mut res = db.query(sql)
        .bind(("repo_id", repo_id))
        .bind(("file", file_rid))
        .bind(("hops", max_hops as i64))
        .await
        .context("collect_file_neighborhood query failed")?;

    // The RETURN is an array of record IDs (e.g. ["file:...","file:..."])
    let ids: Vec<String> = res.take(0)?;
    Ok(ids)
}

pub async fn collect_frag_neighborhood(
    db: &Surreal<Any>,
    repo_id: &str,
    frag_rid: &str,
    max_hops: u32,
    etypes: &[String],
) -> anyhow::Result<Vec<String>> {
    let sql = r#"
        LET $repo = $repo_id;
        LET $seed = $frag;
        LET $et = $etypes;
        RETURN $seed.{..$hops+collect}(
            ->rel[WHERE repo_id = $repo AND etype INSIDE $et]->frag
        );
    "#;

    let mut res = db.query(sql)
        .bind(("repo_id", repo_id))
        .bind(("frag", frag_rid))
        .bind(("hops", max_hops as i64))
        .bind(("etypes", etypes.to_vec()))
        .await
        .context("collect_frag_neighborhood query failed")?;

    let ids: Vec<String> = res.take(0)?;
    Ok(ids)
}

/// Shortest path nodes from one frag to another (unweighted).
pub async fn shortest_path_frags(
    db: &Surreal<Any>,
    repo_id: &str,
    from_rid: &str,
    to_rid: &str,
    etypes: &[String],
    max_hops: u32,
) -> anyhow::Result<Vec<String>> {
    let sql = r#"
        LET $repo = $repo_id;
        LET $from = $from;
        LET $to = $to;
        LET $et = $etypes;

        -- Bound recursion depth so runaway graphs don't explode.
        RETURN $from.{..$hops+shortest=$to+inclusive}(
            ->rel[WHERE repo_id = $repo AND etype INSIDE $et]->frag
        );
    "#;

    let mut res = db.query(sql)
        .bind(("repo_id", repo_id))
        .bind(("from", from_rid))
        .bind(("to", to_rid))
        .bind(("hops", max_hops as i64))
        .bind(("etypes", etypes.to_vec()))
        .await
        .context("shortest_path_frags query failed")?;

    let ids: Vec<String> = res.take(0)?;
    Ok(ids)
}
```

> This uses Surreal’s recursive `+collect` / `+shortest` syntax.  [oai_citation:17‡SurrealDB](https://surrealdb.com/docs/surrealql/datamodel/idioms)  
> And traversal filtering `->imports[WHERE ...]` is consistent with Surreal’s arrow traversal filter pattern.  [oai_citation:18‡SurrealDB](https://surrealdb.com/blog/ten-tips-and-tricks-for-your-surrealdb-queries?utm_source=chatgpt.com)  

### 2) Store method: expand_graph using these helpers
In `ce-store-surreal`, implement `CeStore::expand_graph` like:

- If seeds are `frag:*`:
  - collect frag neighborhood (`collect_frag_neighborhood`)
  - add connector paths if needed (`shortest_path_frags`)
- If seeds are `file:*`:
  - collect file neighborhood (`collect_file_neighborhood`)

### 3) Subgraph selection in packer (high-level)
In `pack` for Surreal backend:

1) seed frags from retrieval (vector/hybrid)  
2) derive seed files via reverse `contains` (either by:
   - querying `frag` record’s `file_id`, or
   - `SELECT VALUE <-contains<-file` via traversal)  [oai_citation:19‡SurrealDB](https://surrealdb.com/docs/surrealdb/models/graph?utm_source=chatgpt.com)  
3) collect file neighborhood
4) fetch key fragments from those files
5) collect frag neighborhood around seeds
6) prune down to budget by:
   - hop distance decay
   - edge weight decay
   - fragment kind priority
