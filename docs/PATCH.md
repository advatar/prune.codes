# Inception Mode implementation

## What “Inception Mode” does

When you start a brand‑new feature/module (or a new repo), the failure mode isn’t “compiler error”—it’s **wrong shape**: wrong folder, wrong patterns, wrong tradeoffs, wrong testing expectations.

Inception Mode gives you:

1) A **one-time (but editable) project preference interview**  
2) A small persistent artifact: `prune.preferences.json` (+ optional decision log)  
3) A new **inception context profile** that always injects those preferences + the repo’s “golden paths” before any design/implementation work

The key is the interview UX: instead of a chat wall, you use a structured wizard UI generated as **A2UI messages**. A2UI is designed specifically so an agent can send a declarative component tree + a data model, and the client renders it with its own native widgets.  [oai_citation:0‡Google Developers Blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)

---

## Protocol choice: A2UI v0.8 (stable)

Use **A2UI v0.8** because it’s explicitly the “stable release, recommended for production use”, and its server→client messages are simple:  
- `surfaceUpdate`  
- `dataModelUpdate`  
- `beginRendering`  
- `deleteSurface`  [oai_citation:1‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

A2UI’s architecture is “LLM-friendly”, uses a flat list of components referencing IDs (adjacency list), and separates UI structure from the data model.  [oai_citation:2‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

---

# Architecture

## High-level flow

### 0) App opens “Inception Wizard”
The SwiftUI app has an “Inception Wizard” screen with:
- repo picker / repo identity
- “Start interview” button

### 1) App starts a local Foundation Models session
Foundation Models gives Swift-native access to an on-device LLM (Apple Intelligence), with guided generation + tool calling; it runs on-device and can work offline.  [oai_citation:3‡Apple](https://www.apple.com/newsroom/2025/09/apples-foundation-models-framework-unlocks-new-intelligent-app-experiences/)

### 2) App sends a prompt: “generate A2UI UI for this repo and these preference questions”
The prompt includes:
- the A2UI v0.8 schema expectations (subset)
- your **client catalog** (what UI components the SwiftUI app supports)
- the **question bank** (canonical preference questions)
- repo metadata (optional but useful): languages/framework hints, directory map, package manifests, etc.

### 3) Model streams A2UI JSONL messages → SwiftUI renderer
A2UI is a JSONL stream; the client buffers `surfaceUpdate` + `dataModelUpdate` and only renders after `beginRendering` to prevent an incomplete flash.  [oai_citation:4‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

### 4) User answers via UI → app emits A2UI `userAction` events back to the agent
A2UI handles user input by sending a client event payload (not in the UI stream). The main event is `userAction` with `name`, `surfaceId`, `sourceComponentId`, `timestamp`, and resolved `context`.  [oai_citation:5‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

### 5) On “Finish”, app persists:
- `prune.preferences.json` (structured answers)
- optional `prune.decisions.md` (short ADR-like bullets generated by the model)

Then Prune’s inception packing profile always includes this file.

# SwiftUI client implementation

## 1) A2UI runtime in the app

### A2UI message model (v0.8 subset)
A2UI v0.8 messages are envelopes where **exactly one** of these keys exists per JSON line:
- `surfaceUpdate`
- `dataModelUpdate`
- `beginRendering`
- `deleteSurface`  [oai_citation:6‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

You can implement this as:

```swift
// A2UI v0.8 subset envelope
struct A2UIMessage: Codable {
    var surfaceUpdate: SurfaceUpdate?
    var dataModelUpdate: DataModelUpdate?
    var beginRendering: BeginRendering?
    var deleteSurface: DeleteSurface?
}

struct SurfaceUpdate: Codable {
    var surfaceId: String?
    var components: [A2UIComponentInstance]
}

// Each instance has an id + a "component" object containing exactly one key,
// whose name is the component type (from your catalog).
// That "exactly one key" constraint is part of the protocol model.  [oai_citation:7‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)
struct A2UIComponentInstance: Codable {
    var id: String
    var component: [String: JSONValue]   // decode dynamically (type keyed)
}

struct BeginRendering: Codable {
    var surfaceId: String?
    var catalogId: String?
    var root: String
}

struct DeleteSurface: Codable {
    var surfaceId: String
}
```

### Component buffer + data model store
Per spec, store components in a map keyed by id, and store the data model separately.  [oai_citation:8‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

```swift
final class A2UIStore: ObservableObject {
    @Published var ready: Bool = false
    @Published var rootId: String? = nil

    // surfaceId -> (componentId -> instance)
    var components: [String: [String: A2UIComponentInstance]] = [:]

    // surfaceId -> arbitrary JSON data model
    @Published var dataModel: [String: Any] = [:]

    func apply(_ msg: A2UIMessage) { ... }
}
```

### DataModelUpdate (v0.8 typed adjacency list)
A2UI v0.8’s `dataModelUpdate` uses:
- `surfaceId`
- optional `path`
- `contents`: adjacency list entries with typed values (`valueString`, `valueBoolean`, `valueMap`, etc.)  [oai_citation:9‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

You only need a subset for preferences: strings, booleans, numbers, arrays, and maps.

---

## 2) Widget registry: A2UI → SwiftUI views

A2UI is catalog-based: the **client** defines what types exist and maps them to native widgets.  [oai_citation:10‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

Start with a tight “Interview Catalog”:

### Minimal interview catalog (recommended)
- Layout: `Column`, `Row`, `Card`, `Divider`, `Spacer`
- Text: `Text`, `Markdown`
- Inputs: `TextField`, `TextArea`, `Toggle`, `Select`, `MultiSelect`
- Actions: `Button`
- UX: `Progress`, `Badge`, `Callout`

You do *not* need the full standard catalog for the first client—only what your wizard needs.

---

## 3) User interactions: emit `userAction` back to the model

A2UI v0.8 defines `userAction` fields and expects the client to resolve the `context` (including data bindings) before sending.  [oai_citation:11‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

```swift
struct A2UIUserActionEnvelope: Codable {
    var userAction: A2UIUserAction
}

struct A2UIUserAction: Codable {
    var name: String
    var surfaceId: String
    var sourceComponentId: String
    var timestamp: String
    var context: [String: JSONValue]
}
```

In your SwiftUI renderer:
- A “Next” button might have `action.name = "next_step"`
- A “Finish” button has `action.name = "finish_interview"`
- Context includes the full `answers` object or at least a diff

# Local Apple Foundation Model “agent” implementation

## 1) Why the Apple on-device model is a good fit here
Apple describes the on-device model as integrated with Swift, private/offline, with **guided generation** and **tool calling**.  [oai_citation:12‡Apple](https://www.apple.com/newsroom/2025/09/apples-foundation-models-framework-unlocks-new-intelligent-app-experiences/)

This is ideal for:
- generating structured interview UI
- extracting/normalizing preferences
- producing short decision summaries

(You should not rely on it for deep world knowledge; Apple’s own WWDC guidance frames the on-device model as optimized for tasks like summarization/extraction/user input analysis rather than “advanced reasoning”.)  [oai_citation:13‡Apple Developer](https://developer.apple.com/videos/play/wwdc2025/286/)

## 2) Concrete Swift API usage (from public examples)
A common pattern shown by developers is:
- create a `LanguageModelSession()`
- call `respond(to:)` for text, or `respond(to: generating:)` for structured output
- use `streamResponse(...)` for progressive output  [oai_citation:14‡AzamSharp](https://azamsharp.com/2025/06/18/the-ultimate-guide-to-the-foundation-models-framework.html)

Example (non-streaming):

```swift
import FoundationModels

let session = LanguageModelSession()
let response = try await session.respond(to: "Hello")
print(response.content)
```

Structured output via guided generation uses `@Generable()` and `@Guide(...)`.  [oai_citation:15‡AzamSharp](https://azamsharp.com/2025/06/18/the-ultimate-guide-to-the-foundation-models-framework.html)

---

## 3) Recommended approach: guided generation of “A2UI frames”
Instead of asking the model to emit arbitrary JSON strings, define a **Guided Generation type** that represents one A2UI message “chunk” (or a batch of chunks).

Conceptually:

```swift
@Generable()
struct A2UIChunk {
    @Guide(description: "Exactly one of these is non-nil.")
    let surfaceUpdate: SurfaceUpdate?
    let dataModelUpdate: DataModelUpdate?
    let beginRendering: BeginRendering?
}
```

Then drive a loop:
- session streams `A2UIChunk.PartiallyGenerated` (optional)
- as each chunk becomes valid, encode it as JSONL and feed it to your A2UIStore

This aligns with:
- A2UI being a stream of JSON objects (JSONL)  [oai_citation:16‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)
- Foundation Models guided generation producing typed structures reliably  [oai_citation:17‡AzamSharp](https://azamsharp.com/2025/06/18/the-ultimate-guide-to-the-foundation-models-framework.html)

# Preference interview: question set + adaptive followups

## Canonical question IDs (so downstream stays stable)
Even if the UI is dynamic, keep a stable schema for answers. Example:

- `scope.thinSliceDefinition`
- `ux.mobileFirst`
- `ux.a11yLevel`
- `arch.layeringPreference`
- `arch.stateManagementPreference`
- `types.strictness`
- `tests.requiredForFeatures`
- `deps.newDependencyPolicy`
- `workflow.smallPRsPreferred`
- `workflow.commitStyle`

## Data model shape in A2UI
Bind each input to a path like:

- `/answers/types/strictness`
- `/answers/tests/requiredForFeatures`

Because A2UI supports binding values to a data model via paths, and the data model is updated only via `dataModelUpdate`.  [oai_citation:18‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

Once the file exists, you add an **inception profile** that does:

1) Always include:
- `.prune/prune.preferences.json`
- `.prune/prune.decisions.md` (if present)

2) Add an “onboarding pack” layer:
- entrypoints
- folder map summaries
- 1–2 golden-path examples per layer

3) Then do normal retrieval/graph expansion.

That’s how you prevent “wrong pattern” on first implementation.

- Emits `userAction` on button presses (next/back/finish) matching A2UI’s event structure  [oai_citation:19‡a2ui.org](https://a2ui.org/specification/v0.8-a2ui/)

### Foundation model agent
- Can generate the initial interview UI as A2UI messages
- Can react to `userAction` and update UI/data model
- Can output a final “preferences object” suitable for writing

### Prune integration
- Inception profile automatically includes preferences in every inception/design/feature task
- Preferences are small and don’t blow the budget

# Prioritized vNext roadmap for Prune (AST slicing + subgraph selection + eval-driven evolution)

This is a practical “do it in order” plan that maximizes impact per unit effort.

## Phase 1 — AST slicing that actually reduces tokens without losing meaning
**Objective:** get “signature + types + call sites + relevant branches” instead of whole-file dumping.

1) **AST skeletonizer per language pack**
   - Keep: exports/public API, type declarations, function signatures, doc comments
   - Drop: most bodies unless referenced or error-touched
   - Add a “body include policy”: none / referenced-only / top-K relevant blocks

2) **Branch-aware slicing**
   - If task references a symbol or error span, slice to the minimal enclosing node(s)
   - Pull adjacent helper definitions only if referenced

3) **Cross-file type slice**
   - If you include a function, also include the minimal set of type defs it depends on (interfaces/type aliases) rather than the whole types module

**Success metric (Stage A):** token reduction with unchanged “unresolved reference risk”.

---

## Phase 2 — Graph subgraph selection (connected, minimal, and explainable)
**Objective:** choose a *connected* evidence set that explains the task, not just “top-K chunks”.

1) **Subgraph candidate generation**
   - Seed nodes: touched files, mentioned symbols, error file/line hints, entrypoints
   - Expand with weighted edges: import/use/refs/JSX-usage/tsconfig-alias edges

2) **Budgeted subgraph solver**
   - Approximate Steiner tree / prize-collecting walk:
     - minimize: tokens + redundancy
     - maximize: coverage score + connectivity
   - Output: “why included” provenance per fragment

3) **Gating policy**
   - If the solver can’t get a connected subgraph under budget, degrade gracefully:
     - keep the best-connected component + a short “missing links” summary

**Success metric (Stage A):** fewer irrelevant fragments; higher “coverage of touched defs”.

---

## Phase 3 — Eval-driven evolution (DGM-style) over *context strategies*, not tools
**Objective:** automatically discover the best strategy combinations.

1) **SWE-bench runner integration**
   - One command runs:
     - Stage A pack metrics
     - Stage B harness evaluation (optional patch agent)
   - You already outlined the right shape: dataset → checkout base_commit → index/pack → optional agent → harness eval.

2) **Strategy genome**
   - Encode strategy params:
     - pruning aggressiveness
     - edge weights/radii
     - AST skeletonization settings
     - hint extraction weights
     - external reference caps
   - Implement mutation + crossover

3) **Two-tier search**
   - Tier 1: run thousands of Stage A only (fast)
   - Tier 2: shortlist and run Stage B (expensive)

4) **Pareto selection**
   - Promote strategies that dominate on:
     - resolved rate
     - tokens
     - latency
     - missing-def risk

**Success metric:** “best-known” configs per language + per repo archetype.

---

## Phase 4 — Make it product-grade
1) **Strategy registry + auto-selection**
   - “bugfix”, “feature inception”, “refactor”, “integration”
2) **Repo-specific memory (decisions + golden paths)**
3) **Full provenance output**
   - every included fragment has a “why” string

---

## Where Inception Mode fits in this roadmap
Inception Mode is a “Phase 4 quality multiplier,” but it benefits immediately from:
- Phase 1 (AST skeletonization) to keep onboarding packs tiny
- Phase 2 (subgraph selection) to keep “golden paths” relevant
- Phase 3 (evolution) to tune inception profiles for different repo types
