# Strategies for Context Engineering in LLM-Powered Coding Assistants

Large language models (LLMs) for code (like OpenAI Codex or Code Llama) are most effective when given the right context from a codebase. However, context windows are limited, and stuffing too much code or irrelevant information can degrade performance (often called *context rot*) [oai_citation:0‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=Despite%20rapid%20progress%20in%20reasoning,horizon%20tasks). Moreover, long prompts drastically increase computation and cost. Therefore, **context optimization is essential for both accuracy and cost-efficiency**. Below we explore a comprehensive set of strategies – known and emerging – for **Context Engineering** in coding agents. These range from summarizing or trimming context, to smart retrieval of relevant code, to structural and graph-based methods, and even novel ideas inspired by languages like Unison.

## Summarization and Context Compaction

One straightforward approach to managing context is **summarization or compaction** of the prompt. In this paradigm, once the context grows beyond a threshold, older or less relevant parts are condensed into a shorter summary. This technique has been used in some long-chat or coding scenarios (e.g. summarizing earlier conversation or code state) to free up space for new information [oai_citation:1‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=typically%20task,make%20room%20for%20new%20content). The built-in compaction of many LLM-based tools typically uses this method: they recursively summarize earlier content to maintain a sliding window of important facts.

- **Advantages:** Summarization can significantly reduce prompt length and keep only high-level facts. It’s simple to implement by prompting the LLM itself to produce summaries, or using an external summarization model. OpenAI’s early Codex CLI, for example, reportedly summarized long interactive sessions to keep prompts short [oai_citation:2‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=typically%20task,make%20room%20for%20new%20content).

- **Limitations:** The major risk is that **important details may be lost**. Summaries are by nature abstractions – if a coding task later requires a small detail that was “forgotten” in a summary, the model’s answer will suffer. Research has noted that such **context condensation is not expressive enough for rich tasks** that require dense access to many parts of the prompt [oai_citation:3‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=typically%20task,make%20room%20for%20new%20content). In other words, assuming that some details “can safely be forgotten” often breaks long-horizon code understanding tasks. Summaries also can introduce inaccuracies or generalizations that mislead the model.

Because of these issues, summarization alone is usually insufficient for complex coding scenarios. It may work for simple contexts (e.g. remembering function names or high-level goals) but struggles when many interdependent details matter. Thus, more targeted context management strategies are used in practice.

## Retrieval-Augmented Context (RAG) for Code

A more powerful class of strategies falls under **Retrieval-Augmented Generation (RAG)** for code. Instead of (or in addition to) summarizing, the idea is to **fetch only the relevant pieces of code or documentation from a repository** and supply those to the LLM on the fly. This way, the prompt contains *only* the facts needed to answer the current query or generate the next code snippet, rather than an entire codebase.

Modern coding assistants like Sourcegraph’s Cody and Amazon CodeWhisperer have a “context engine” that implements retrieval. For example, Sourcegraph’s AI assistant explicitly treats **context retrieval as a search problem**: given a user query, it searches the codebase for the most relevant files, functions, or comments, and includes those snippets in the prompt [oai_citation:4‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=The%20context%20engine%20is%20conceptually,handling%20of%20unauthorized%20responses%2C%20etc) [oai_citation:5‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=happens%20when%20authorization%20fails%2C%20and,how%20tokens%20are%20processed). This approach is akin to giving the LLM a customized reference manual for each query [oai_citation:6‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=In,makes%20LLMs%20so%20versatile%E2%80%94they%20can). By using the right context, the model can answer with specific details about *your* code rather than generic knowledge [oai_citation:7‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=To%20go%20from%20LLM%20to,code%2C%20architecture%2C%20and%20development%20practices).

**How retrieval works:** Typically, a two-stage pipeline is used [oai_citation:8‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=The%20context%20engine%20operates%20in,This%20separation%20of):

1. **Retrieval Stage (Recall-focused):** Use fast, broad search techniques to gather candidate snippets (context items) that might be relevant. This can include keyword search, regex matching, or vector similarity search on code embeddings. The goal is high recall – find anything potentially useful, even if the list is noisy.

2. **Ranking Stage (Precision-focused):** Use a more refined model (often an ML model or heuristic scoring) to rank the candidate snippets by relevance, and select the top ones that fit the token budget. This stage ensures only the most relevant context is kept, filtering out noise [oai_citation:9‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=A%20unique%20aspect%20of%20our,most%20relevant%20context%29%20while) [oai_citation:10‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=The%20ranking%20layer%20acts%20as,we%27re%20not%20only%20wasting%20our). It can be framed as a *knapsack problem* – pick the most “valuable” pieces of context that maximize relevance without overflowing the prompt limit [oai_citation:11‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=match%20at%20L234%20A%20unique,most%20relevant%20context%29%20while) [oai_citation:12‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=A%20unique%20aspect%20of%20our,most%20relevant%20context%29%20while). Sourcegraph, for instance, trains a Transformer-based ranker to predict which snippets are truly relevant to the query [oai_citation:13‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=Ranking%20is%20oftentimes%20done%20with,have%20a%20score%20for%20each).

**Embedding-based and lexical retrieval:** There are multiple ways to implement the retrieval step:

- *Lexical search:* Searching for keywords, function names, or symbols in the code (possibly using an index like Sourcegraph’s code search or grep). This is fast and often effective since code queries contain specific identifiers. In fact, one study found that a simple **symbol overlap (Jaccard similarity) search outperformed more complex neural embeddings** for code retrieval in many cases [oai_citation:14‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=We%20experimented%20with%20multiple%20methods,leave%20this%20as%20future%20work). Lexical search ensures exact matches (e.g., if the query mentions `UserService`, find files where `UserService` is defined or used).

- *Semantic embedding search:* Using vector embeddings of code (from a model like CodeBERT, CodeSearcher, or OpenAI’s text-embedding-ada for code) to find semantically similar code snippets. This can catch relevant context even if exact keywords differ (for example, two functions that do similar things with different names). Many systems use a combination: semantic search to find conceptually related code and lexical search for exact identifier matches – merging results from both before ranking.

- *Hybrid and specialized retrieval:* Recent work suggests using **structure-aware retrieval**, where code is indexed not just as raw text but with awareness of its structure (more on this in the next section). For example, Amazon researchers tried advanced techniques like UniXcoder (a Transformer-based code embedding model) and CodeBLEU (which incorporates syntax trees and code flow) for retrieval, but these didn’t beat a basic symbol overlap method in their experiments [oai_citation:15‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=We%20experimented%20with%20multiple%20methods,leave%20this%20as%20future%20work). They hypothesize that a better approach is to chunk code along structural boundaries (functions, classes) and embed those – which could improve semantic retrieval’s precision [oai_citation:16‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=We%20experimented%20with%20multiple%20methods,leave%20this%20as%20future%20work). This leads into structural chunking strategies.

**Selective retrieval to reduce overhead:** An interesting finding is that **retrieval is not always needed**. If the code immediately around the cursor already contains enough information (or the model’s intrinsic knowledge suffices), doing a repository search can be wasteful or even distract the model with redundant context. In an ICML 2024 paper, “Repoformer,” Amazon researchers noted that *in about 80% of code completion cases, cross-file retrieval did not improve the result* [oai_citation:17‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=its%20outputs,it%20always%20the%20best%20choice). In those cases, the model could complete code correctly using just the local file context. However, always performing retrieval incurs a latency penalty (fetching and processing the extra snippets) for little gain in those scenarios [oai_citation:18‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=Retrieval,it%20always%20the%20best%20choice).

To address this, they trained a **policy model to decide when retrieval is actually helpful**. This small model looks at the current code and predicts whether adding external context would improve the outcome. If not, the system skips retrieval and just uses the base LLM; if yes, it retrieves and provides that context. The Repoformer approach achieved a **70% speedup by avoiding unnecessary retrievals**, *while actually improving overall accuracy* (because the model was less distracted by irrelevant info) [oai_citation:19‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=In%20experiments%2C%20we%20found%20that,and%20different%20code%20completion%20tasks). Essentially, **selective retrieval** means the agent learns to only pay the cost of extra context when it’s worth it.

**Filtering and trimming retrieved context:** Even when retrieval is used, not everything it fetches is useful. Some retrieved code fragments may be irrelevant or even misleading for the current task. Including such snippets wastes prompt space and can confuse the LLM (leading to poorer answers). A 2025 study introduced a framework called **CodeFilter** that tackles this issue [oai_citation:20‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=cross,retrieved%20contexts%20in%20code%20completion). The idea is to evaluate each retrieved chunk’s *impact* on the completion: does adding this chunk help the model predict the code correctly, have no effect, or actually hurt? They label retrieved code pieces as *positive* (helpful), *neutral*, or *negative* based on a likelihood-based metric of contribution [oai_citation:21‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=cross,retrieved%20contexts%20in%20code%20completion). Using these labels, they train a filter model to **discard irrelevant or harmful context before prompting the LLM** [oai_citation:22‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=address%20this%20issue%2C%20we%20leverage,Additionally).

CodeFilter was shown to **improve code completion accuracy by filtering out the noise**, and notably it also *reduces the prompt length significantly* (since many unhelpful chunks are dropped) [oai_citation:23‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=address%20this%20issue%2C%20we%20leverage,Additionally) [oai_citation:24‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=demonstrates%20that%20CODEFILTER%20consistently%20improves,while%20exhibiting%20strong%20generalizability%20across). This confirms a key point in context engineering: *more context is not always better* – the quality and relevance of context matters more than sheer quantity. An optimal system strives to supply the *minimal necessary context* that covers all essential information and nothing extra.

In summary, retrieval-augmented methods form the backbone of many coding assistants today. They **augment the LLM’s short-term memory with an external search** over the codebase. By intelligently deciding *what* to retrieve and *when*, and filtering results, such systems keep the context focused and concise, improving both accuracy and speed.

## Structural Code Chunking and AST-Based Context

A crucial insight for code is that it has much more structure than free text. We can exploit the programming language’s syntax and semantics to *engineer context more intelligently* than just chopping text at a fixed length. Two key techniques here are **AST-aware chunking** of code and using dependency analysis to gather related snippets.

**AST-aware chunking:** Rather than splitting files into arbitrary 500-token blocks or paragraphs, we can chunk code along its *Abstract Syntax Tree (AST)* boundaries. In practice, this means each chunk corresponds to a logical code unit – e.g. a function, a class, or a logical block – instead of random slices of text. This approach is used by tools like *code-chunk* (which employs Tree-sitter for parsing) to create self-contained code fragments for embedding and retrieval [oai_citation:25‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=1) [oai_citation:26‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=4):

- The code is first **parsed into an AST**, giving a structured representation of definitions and scopes [oai_citation:27‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=1).
- The chunker then **extracts semantic entities**: functions, methods, classes, interfaces, types, imports, etc., along with their names and signatures [oai_citation:28‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=2).
- It organizes these entities in a **hierarchical scope tree**, understanding nesting (e.g. which class a method belongs to) [oai_citation:29‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=3).
- Finally, it **splits the code at semantic boundaries**, aiming to keep each chunk as a whole entity (a function or a group of small related functions) and never cutting in the middle of an expression or statement [oai_citation:30‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=4). If an entity is too large, it will split at logical breakpoints (e.g. between function bodies or paragraphs of code) but still respect syntax.

Each chunk can be *enriched with metadata* about its context: for example, you can prepend a header to the chunk text indicating the file path, the scope (which class or module this is in), the function signature, and which symbols it imports or uses [oai_citation:31‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=Each%20chunk%20is%20enriched%20with,contextual%20metadata) [oai_citation:32‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=The%20,to%20the%20raw%20code). This metadata effectively provides a summary of “what this chunk is” so that even if retrieved alone, the LLM knows the context (e.g. *“This is from src/services/user.ts, inside class `UserService`, defining method `getUser`, which uses `Database`”* [oai_citation:33‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=The%20,to%20the%20raw%20code)).

**Benefits of AST/structural chunking:**

- *Coherence:* Chunks are logically coherent units. The LLM won’t see half a function definition missing its end, or a random snippet of a class in isolation – each chunk is as self-contained as possible. This makes retrieved context far more understandable and useful to the model.

- *Reduced fragmentation:* By merging small functions together and avoiding splitting large ones arbitrarily, you typically get fewer chunks overall [oai_citation:34‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=,adjacent%20chunks%20to%20reduce%20fragmentation). This means fewer pieces to retrieve and concatenate, which helps stay within token limits.

- *Rich context for embeddings:* Because we include semantic annotations (“scope: X”, “defines: Y”, “uses: Z”) in the chunk text, the embedding model has more to latch onto. It can understand relationships like *“function getUser is defined inside class UserService”* or what external symbols are referenced. This leads to more accurate similarity searches – e.g., if a query asks about `getUser`, an embedding of a chunk that has “defines: getUser” will closely match. The chunks are essentially *pre-chewed* for the vector database, capturing important code relationships in text form [oai_citation:35‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=Each%20chunk%20is%20enriched%20with,contextual%20metadata).

- *Multi-language support:* By using a parser for each language, this technique can be applied beyond just one language. In fact, code-chunk supports TypeScript, Python, Java, Go, Rust, etc., each with language-specific AST parsing [oai_citation:36‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=%2A%20AST,class%20Effect%20integration). The concept remains the same: treat code as structure, not just text.

**Dependency-based inclusion:** Another structural approach is to use the code’s dependency graph to decide context. In a codebase, functions and classes reference each other via calls, imports, or inheritance. If a user asks a question or if the LLM is generating code that touches multiple components, we can **traverse these links to gather relevant definitions** automatically. For example:

- *Imports and includes:* If the current file imports module X, and the query involves something from X, the assistant can pull in the content (or the docs) of X’s definitions. This is akin to an IDE’s “go to definition” – the agent sees a symbol and fetches its definition from elsewhere in the project. Some research prototypes let an LLM do this by itself: the LLM output can include instructions like “(please open file X to get the definition of Y)” which an external tool then executes, feeding the result back into the prompt [oai_citation:37‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=As%20Figure%C2%A02%20illustrates%2C%20an%20RLM,they%20can%20invoke%20themselves%20recursively) (this is similar in spirit to RLM and will be discussed later).

- *Call graphs:* If generating or analyzing a function that calls `foo()`, and `foo` is defined in another file, the context builder can retrieve `foo`’s source. Or if examining a class method that overrides a base class, including the base class signature could be helpful.

A concrete implementation along these lines is described by Tencent in their “Identifier-based RAG” system for code completion. They use a powerful base LLM to first **analyze the code snippet and identify what symbols (functions, classes, protobuf messages, etc.) are likely needed** to complete it [oai_citation:38‡arxiv.org](https://arxiv.org/html/2507.18515v1#:~:text=%23%20%20II,Extraction). Essentially, the model itself is prompted to output a list of “go fetch these definitions for me.” Once those identifiers are extracted, the system looks them up in an indexed code database and retrieves, say, the function definitions, class definitions, or type declarations that correspond [oai_citation:39‡arxiv.org](https://arxiv.org/html/2507.18515v1#:~:text=To%20facilitate%20efficient%20retrieval%2C%20we,the%20identifier%20and%20search%20type) [oai_citation:40‡arxiv.org](https://arxiv.org/html/2507.18515v1#:~:text=The%20second%20step%20leverages%20a,extracts%20three%20sets%20of%20identifiers). Those retrieved pieces are then assembled into the final prompt given to the LLM to generate the completion. This approach ensures that **only code that the model explicitly deems relevant is included**. It’s a clever merging of static analysis with the model’s own understanding: the LLM might know from context that “we are likely calling `processPayment`, defined elsewhere, better get it.” The result is a focused prompt containing exactly the needed API contracts or usages.

By leveraging AST structure and dependency graphs, context engineering goes beyond plain text search. These methods treat the codebase as a well-structured knowledge source. The outcome is often a **smaller, more relevant prompt** that provides the model with *just the right functions, classes, or constants it needs*, along with the contextual cues to understand how they all connect.

## Knowledge Graphs and Graph-Based Context Retrieval

Taking the structural idea even further, researchers have explored using **graphs to represent entire codebases** and to retrieve context via graph queries. The motivation is that code isn’t just flat text; it’s a network of relationships – functions call other functions, classes inherit from other classes, modules depend on each other, etc. If we encode this as a graph (a knowledge graph of code), we can then ask very precise questions like “find all nodes related to X” or “give me the subgraph around feature Y” and use that as context for the LLM.

A recent 2025 approach outlines a three-step pipeline for **graph-based context retrieval** in repository-level code generation [oai_citation:41‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=Image%3A%20Refer%20to%20caption%20Figure,as%20context%20to%20the%20LLM):

1. **Code -> Knowledge Graph:** First, convert the entire code repository into a knowledge graph where **nodes** represent code entities (functions, classes, files, modules, maybe even variables) and **edges** represent relationships (e.g. “Function A calls Function B”, “Class C extends Class D”, “File X imports Module Y”) [oai_citation:42‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=Image%3A%20Refer%20to%20caption%20Figure,as%20context%20to%20the%20LLM) [oai_citation:43‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=generation%20with%20LLMs,accurate%20and%20contextually%20aware%20code). This graph captures the hierarchical structure and dependency links of the codebase in a formal way.

2. **Graph-Based Retrieval:** When a user poses a query or a generation task (e.g. “Implement feature X that integrates A and B”), use a hybrid retrieval approach to **find a relevant subgraph** that pertains to this query [oai_citation:44‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=repository%20into%20a%20knowledge%20graph%2C,as%20context%20to%20the%20LLM) [oai_citation:45‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=generation%20with%20LLMs,accurate%20and%20contextually%20aware%20code). This might involve:
   - Performing a semantic search on node content or documentation (like vector search on code or doc embeddings attached to graph nodes).
   - Using the query to identify an initial set of pertinent nodes (perhaps via keyword match: e.g. nodes with names or docstrings matching “Authorization” if the query is about an auth system).
   - Expanding that set along the graph edges to include directly related entities (dependencies or dependents, etc.). For instance, if a function is relevant, also grab functions that call it or that it calls, and its class, etc., up to a certain radius.
   - The end result is a *refined subgraph* – a collection of code entities and their relationships that are likely needed for the task at hand.

3. **Provide Subgraph as Context:** Finally, serialize this subgraph (or the code snippets corresponding to its nodes) into a prompt for the LLM [oai_citation:46‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=Image%3A%20Refer%20to%20caption%20Figure,as%20context%20to%20the%20LLM). This could mean listing the key classes/functions and their content, along with short descriptions of how they connect (or some structured format the LLM is trained to understand). The LLM then generates code with awareness of this provided context.

Such a system can yield **very rich contextual information** that goes beyond unstructured text. For example, because the graph inherently carries *relational* info, the prompt can explicitly tell the model: *“Function X is a helper used by Y. Class C implements interface I. These two components interact via Z.”* This helps the LLM understand the bigger picture and maintain consistency. The authors note that this kind of **contextual, usage-based representation leads to more functionally correct and stylistically consistent code generation**, since the model sees not just code snippets but also how they fit into the project structure [oai_citation:47‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=downstream%20tasks%20such%20as%20code,existing%20code%20to%20minimize%20duplication) [oai_citation:48‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=By%20capturing%20the%20usage%20of,required%20to%20align%20generated%20outputs). It reduces errors and duplication because the model is guided to reuse existing functions and follow existing patterns [oai_citation:49‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=to%20information%20retrieval%20on%20code,existing%20code%20to%20minimize%20duplication).

Several research prototypes embody aspects of this idea:

- **GraphCoder (2024)** – This approach constructed a *Code Context Graph (CCG)* for a repository, where nodes might represent code statements or blocks and edges the control or data flow between them. At inference time, GraphCoder retrieves relevant portions of this graph to supply the LLM with in-context examples for code completion [oai_citation:50‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=GraphCoder,to%20provide%20LLMs%20with%20better). It essentially gives the model a slice of the program’s flow around the area being completed, so it can see how variables and calls connect. GraphCoder showed improved repository-level code completion by incorporating these graph snippets.

- **CodeXGraph (2024)** – In this framework, the entire repository is converted into a knowledge graph (with a custom schema for code). They then use an LLM as a query planner: the user’s natural language query is transformed into a graph query (for example, the LLM could generate Cypher or another query language to search the code graph) [oai_citation:51‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=Knowledge%20graphs%20have%20emerged%20as,Similarly%20aligned%20with%20our%20proposed) [oai_citation:52‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=GraphCoder,the%20repository%20to%20a%20knowledge). The query is executed on the knowledge graph to retrieve the relevant code nodes, which are then fed back into the LLM for answer generation. This is a form of tool use: the LLM effectively “asks” the graph for what it needs. CodeXGraph was shown to work well for question-answering and simple generation tasks on code, efficiently bridging natural language and code structure.

- **Knowledge-augmented code QA/generation systems** – Beyond named papers, we see a general trend of using code knowledge graphs in industry. For instance, systems could integrate with **code graphs from tools like Sourcegraph’s Code Intelligence (which builds a code graph for IDE features)**. Microsoft’s recent “GraphRAG” concept also hints at using graph-structured knowledge in retrieval augmented generation [oai_citation:53‡github.com](https://github.com/microsoft/graphrag#:~:text=microsoft%2Fgraphrag%3A%20A%20modular%20graph,code%20serves%20as%20a). The idea is that a graph can encode domain knowledge (here the code’s architecture) that can be queried and combined with text retrieval for superior results [oai_citation:54‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=generation%20with%20LLMs,accurate%20and%20contextually%20aware%20code).

The graph-based approach is powerful but also complex. Building and maintaining a code knowledge graph can be heavy, and translating arbitrary user questions into graph queries is non-trivial. However, for large, complex codebases, this might be a game-changer: instead of dumping thousands of lines of code into a prompt, the assistant can provide a *surgically precise* context that includes **the relevant code and a map of how that code connects together**. This yields thorough understanding with far fewer tokens.

## Recursive and Agent-Based Context Management

Another frontier in context engineering is letting the *model itself* manage and explore context in a **recursive or agentic manner**. Instead of one giant prompt, the model operates in a loop, considering pieces of the input step by step. This is akin to giving the model tools or the ability to *autonomously decide which part of the context to read next*. Two notable categories here are **Recursive Language Models (RLMs)** and more general multi-agent or tool-using frameworks for code.

**Recursive Language Models (RLMs):** Introduced by Zhang, Kraska, and Khattab (2025) [oai_citation:55‡arxiv.org](https://arxiv.org/abs/2512.24601#:~:text=Title%3ARecursive%20Language%20Models) [oai_citation:56‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=We%20introduce%20Recursive%20Language%20Models,LLM%20can%20symbolically%20interact%20with), RLMs represent a paradigm shift in handling long contexts. The key idea is to **treat the prompt as an external data source (an environment)** that the model can interact with, rather than something that must be fed in full to the neural network [oai_citation:57‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=We%20introduce%20Recursive%20Language%20Models,LLM%20can%20symbolically%20interact%20with). In an RLM setup, when given an extremely long input (say a codebase or a lengthy specification), the model isn’t simply asked to digest it end-to-end. Instead:

- The system starts a **REPL (Read-Eval-Print Loop) environment** and loads the entire input (prompt) into a variable in that environment [oai_citation:58‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=As%20Figure%C2%A02%20illustrates%2C%20an%20RLM,they%20can%20invoke%20themselves%20recursively). For instance, the prompt might be accessible via a variable `P` as a string.

- The LLM is then prompted to **write code (in some scripting language like Python)** that can *inspect and manipulate that variable*. In other words, the model’s output is not the final answer yet, but rather an intermediate program or set of instructions.

- The model can generate code to, say, **peek at a certain segment** of the prompt (e.g., read the first 1000 tokens, or search within `P` for a keyword and extract the surrounding text), or **divide the task**: it might determine that the prompt consists of multiple parts (like multiple files or sections of a document) and create subtasks to process each part separately.

- Crucially, the model can then **call itself recursively** on those smaller snippets of the prompt [oai_citation:59‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=prompts%20through%20the%20lens%20of,cost%20per%20query) [oai_citation:60‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=We%20introduce%20Recursive%20Language%20Models,LLM%20can%20symbolically%20interact%20with). For example, if `P` contains 1 million tokens of code, the model might output code like: *“for each file in the codebase (split by some delimiter), call the LLM on that file to get a summary or answer relevant to that file.”* Each recursive call is given a portion of `P` that fits in the standard context window. The top-level process (the REPL) then can combine or reason over the results of these recursive calls.

In essence, **RLM turns the one-shot prompting into an *algorithmic process***. The model is both reading and writing its context in pieces, guided by its own generated code. It externalizes the long context handling into a form of programmatic control flow. Notably, *this requires no modification of the underlying LLM architecture* – it’s an *inference-time strategy* using the model in a loop with itself [oai_citation:61‡arxiv.org](https://arxiv.org/abs/2512.24601#:~:text=,scaffolds%20across%20four%20diverse%20long) [oai_citation:62‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=We%20introduce%20Recursive%20Language%20Models,LLM%20can%20symbolically%20interact%20with). RLMs have demonstrated the ability to handle inputs **orders of magnitude larger than the native context window** of the model, by this recursive divide-and-conquer [oai_citation:63‡arxiv.org](https://arxiv.org/abs/2512.24601#:~:text=,scaffolds%20across%20four%20diverse%20long) [oai_citation:64‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=find%20that%20RLMs%20successfully%20handle,cost%20per%20query). Even for shorter prompts, RLM often **improves quality** because the model can focus deeply on one chunk at a time and maintain more detail, rather than suffering context dilution over a long input [oai_citation:65‡arxiv.org](https://arxiv.org/abs/2512.24601#:~:text=,scaffolds%20across%20four%20diverse%20long) [oai_citation:66‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=Despite%20rapid%20progress%20in%20reasoning,horizon%20tasks).

In experiments, a GPT-5 based RLM could process 10 million+ tokens of input and still answer questions accurately, dramatically outperforming vanilla long-context methods like simple compaction or retrieval-based agents [oai_citation:67‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=understanding%C2%A0,less%20severe%20degradation%20for%20longer). In fact, RLM outperformed other long-context approaches (including summary-based compaction, retrieval tool use, and prior code agents) by **double-digit percentage points on accuracy** in various tasks, all while having comparable or lower total compute cost [oai_citation:68‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=understanding%C2%A0,less%20severe%20degradation%20for%20longer). This is a striking result – it suggests that carefully letting the model *manage its own attention* via code can beat even feeding a big context into an expanded context model.

To ground this in an example: imagine an LLM-based code assistant asked to answer a question about a very large code repository. A traditional approach might retrieve some files and stuff as much as possible into the prompt. An RLM approach might instead have the model generate a plan like: *“There are 50 files. These files seem to be organized into modules A, B, C… The question pertains to functionality in module B. Let’s open the index of module B. Now find in that module the function related to X. Summarize that function. Also, find all references to that function across the codebase.”* The model would call itself to summarize or extract as needed, then finally produce an answer. This way, the model effectively *navigates the codebase* rather than passively reading a pre-selected slice.

**Agent-based and iterative frameworks:** Beyond RLM, there is a broader class of coding “agents” that manage context through planning and multiple steps. Many of these predate RLM and were inspiration for it, though they often required custom logic or had limitations. For instance:

- **Plan-and-Solve Agents:** Approaches like OpenAI’s early code agents or Anthropic’s “Claude code subagents” concept (as referenced in RLM) allowed the model to break a problem into sub-problems. One agent might outline steps (e.g., “Step 1: open file X, Step 2: find function Y, Step 3: verify Z”), and then execute them, possibly calling the LLM for each step. The limitation was that if any step required looking at a part of the input beyond the context window, they were stuck – these agents didn’t circumvent the context length, they just structured the thinking.

- **RepoFusion (2023):** This approach retrieved multiple chunks from a repository and then used a *Fusion-in-Decoder (FiD)* model to combine them in the prompt for generation [oai_citation:69‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=files%20in%20the%20repository%20by,in%20computational%20scalability%2C%20limiting%20its). Essentially, it tried to incorporate *several* context pieces by letting the decoder attend across them (FiD is a technique from open-domain QA). It improved accuracy over single-chunk retrieval. However, as the authors note, **RepoFusion ran into scalability issues** – combining many chunks made inference slow and heavy, so it’s hard to scale to truly huge contexts [oai_citation:70‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=heavily%20relies%20on%20the%20amount,intensive%20settings).

- **AgentCoder (2023):** An example of a multi-agent refinement approach for code generation [oai_citation:71‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=Recent%20research%20has%20introduced%20agentic,overhead%20due%20to%20iterative%20refinement). AgentCoder had different agents (sub-models or sub-routines) with roles like Code Writer, Tester, Optimizer. The idea is the Code Writer generates code, the Tester agent runs or analyzes it (maybe identifies bugs or failing test cases), then the Optimizer improves it, and this cycle continues. By iteratively refining, it can handle more complex requirements. However, **coordinating multiple agents is complex and incurs overhead** [oai_citation:72‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=Recent%20research%20has%20introduced%20agentic,overhead%20due%20to%20iterative%20refinement). If each agent invocation has a context limit, they might still need to exchange summaries or partial info. This approach improves quality but doesn’t inherently solve the context length issue; it just breaks the task into stages.

The common theme is *decomposition*: handling large or complex inputs by breaking them into smaller pieces and possibly handling each piece separately. RLM provides a general recipe to let the model itself do this in a flexible way, rather than relying on a fixed number of agents or a static pipeline.

**Tools and function-calling:** A related technique is leveraging the model’s ability to use external **tools or functions**. For example, OpenAI function calling could allow a coding agent to call a `search(query)` function or a `get_file(path)` function. The model might generate a function call like `get_file("util.py")` when it needs more context from that file, and the system would insert the file’s contents (or a summary) into the conversation. This is a form of *on-demand retrieval* driven by the model. It’s somewhat analogous to RLM, but with discrete tools: the model doesn’t write an arbitrary program, it just calls predefined actions. This approach is seen in some experimental assistants: the model has a tool like “open a file by name” or “search for a symbol”, enabling it to dynamically gather more information beyond its initial prompt. While this requires setting up those tools, it can greatly enhance context flexibility – the prompt no longer has to include everything upfront, because the model can pull in new data mid-session.

In summary, recursive and agent-based strategies aim to overcome the fixed context window by making the process **iterative and interactive**. They either have the model *figure out what parts to read next*, or use multiple passes and agents to refine and incorporate information gradually. These methods, especially RLM, have shown that we can scale to essentially unbounded context lengths and solve problems that were previously infeasible with a single prompt. The trade-off is that these approaches introduce complexity – they turn a one-shot prompt into a multi-step process. Ensuring reliability (the model could make a mistake in its own planning code) and efficiency in these loops is an active area of research. But as context windows increase and yet still prove insufficient (we’ve seen models with 100K token windows, but even those can struggle with truly massive codebases or long documents due to *context rot* [oai_citation:73‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=Despite%20rapid%20progress%20in%20reasoning,horizon%20tasks)), these intelligent strategies will be key for the next generation of coding assistants.

## Content-Addressable Code and Novel Compression Ideas

So far, we’ve discussed methods that either **prune** context (summarization, filtering), **retrieve** relevant context, or **split** context into manageable pieces. Another angle to consider is changing *how we represent context* to make it more compact. One intriguing inspiration comes from the **Unison programming language** and its concept of content-addressable code.

**Unison’s big idea:** *“Each Unison definition is identified by a hash of its syntax tree. Put another way, Unison code is content-addressed.”* [oai_citation:74‡renato.athaydes.com](https://renato.athaydes.com/posts/unison-revolution.html#:~:text=In%20their%20words%2C%20here%20it,is). In Unison, every function or type is stored in a database indexed by a hash of its AST. If two functions have identical implementation, they share the same hash and are essentially the same entity in the system. Code is never duplicated in text form; references to code are done via hashes (and the system can have multiple human-readable names pointing to the same hash). The codebase is like a big Merkle tree of AST nodes [oai_citation:75‡renato.athaydes.com](https://renato.athaydes.com/posts/unison-revolution.html#:~:text=Code%20is%20not%20stored%20in,similar%20to%20a%20Git%20repository).

Why is this relevant for context engineering? Because it suggests a way to **avoid repetitive or unnecessary code in the prompt**. If we had a similar content-addressable store for a codebase, a coding agent could include a *reference* to a piece of code rather than the full text every time. For example, imagine an assistant trying to explain or modify a widely-used utility function. The first time, it fetches the function’s code (by hash or ID) and includes it in the prompt. But if that function is needed again (or was already present in context), the assistant could simply refer to it by an identifier. In an extreme case, one could envision a prompt saying: *“Consider function `F#abc123` (see definition above). Now here is a new usage of `F#abc123` in another file...”* – the model sees a token or small identifier instead of the entire function body again. This is a form of **lossless compression**: the identifier stands in for potentially hundreds of tokens of code.

Of course, a raw LLM doesn’t inherently understand a hash like `#abc123` means some code – you’d need to either fine-tune it to recognize and expand those references, or, more practically, handle it with a tool mechanism. For instance, the assistant could have a function `insert_code(hash)` that the model can call to retrieve the actual code for that hash. This is similar to the tool-use concept above, but leveraging the idea that *the same code won’t be sent twice*. If an assistant is working within a known repository, it could establish a map of content hashes to code snippets at the start of a session. Then the prompt can be made much smaller by using those placeholders. It’s as if the prompt had an *included library* of code that the model can indirectly access.

Beyond hashing, the general principle is **deduplication and reference**. In large projects, many functions or patterns repeat. Rather than feeding duplicates into the model, we give it one canonical copy and refer back to it. Some current techniques do a simpler version: e.g., collapsing identical or very similar chunks in retrieval results (“we found 5 files all containing the same boilerplate – include it once with a note that it appears elsewhere”). A content-addressable approach could automate this.

Additionally, Unison’s approach of storing code in a database and linking definitions by hash means you always know *exactly* which definitions are impacted by which others [oai_citation:76‡renato.athaydes.com](https://renato.athaydes.com/posts/unison-revolution.html#:~:text=definitions%20by%20its%20hash) [oai_citation:77‡renato.athaydes.com](https://renato.athaydes.com/posts/unison-revolution.html#:~:text=When%20you%20change%20the%20type,fine%20too%21%20It%E2%80%99s%20your%20choice). For a coding AI, this could translate to a precise dependency graph to traverse (as discussed in structural methods). It also ensures consistency – if the model suggests a change to a function, all call sites could be flagged via the hash links.

Another novel idea related to context compression is **symbolic representations or abstractions**. For example, instead of including a whole class implementation, the assistant might include only its interface or type signature if the question doesn’t require the implementation details. In many cases, the *declaration* of a function (its name, parameters, return type, docstring) carries enough context for the model to proceed, and the *body* can be omitted unless needed. This is akin to how a human programmer might not crack open a library function unless they need to know its internals – otherwise the name and docs are sufficient to use it. An intelligent context engine could do the same: start by providing high-level information (signatures, docs) for related code, and only pull in full implementations if the task demands it. This staged disclosure keeps prompts concise.

**Learning-based compression:** There is also the possibility of using a smaller model or an encoding scheme to compress a large context into a shorter form that the big LLM can decode. For instance, one could train an autoencoder on code or text such that a 10,000-token document is encoded into a 1000-token “summary” that is not human-readable but *is* understandable by a decoder model. This is speculative, but some research in learned token compression or progressive summarization hints at it. Essentially, rather than a human-readable summary (which might lose info), it could be a machine-generated abstract representation that preserves details in fewer tokens. The main LLM could be augmented to accept such compressed representations (perhaps via an adapter or special prompting). However, this is quite complex and not mature in current literature.

In practice, many of the “unknown” or future strategies will likely combine the ideas above. For example, an agentic approach might use content-addressable references: the agent decides to label a chunk of code with an ID, and later when it needs that chunk, instead of reloading it, it just uses the ID, and the external system ensures the model still has access to it (through tool invocation or because it’s still in memory). As context windows grow, one might imagine *hybrid human-AI summarization*, where the model can ask for human-written high-level docs for parts of the code, using those as context instead of raw code (bringing documentation or comments more into the loop of context). The space of possibilities is large, but all share the goal of **maximizing useful information and minimizing fluff** in the prompt.

## Conclusion

**Context engineering for coding agents** is a vital area of research and development, as it directly impacts the quality of code assistance and the feasibility of scaling these tools to real-world projects. We’ve surveyed a wide spectrum of strategies:

- *Basic compaction:* Summarizing or truncating context to fit limits – simple, but risky for detailed code tasks [oai_citation:78‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=typically%20task,make%20room%20for%20new%20content).
- *Retrieval augmentation:* Searching the codebase for relevant snippets so the model only sees what matters – the core of modern code assistants [oai_citation:79‡sourcegraph.com](https://sourcegraph.com/blog/lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation#:~:text=The%20context%20engine%20is%20conceptually,handling%20of%20unauthorized%20responses%2C%20etc). This includes advanced techniques like selective retrieval (to avoid unnecessary overhead) [oai_citation:80‡amazon.science](https://www.amazon.science/blog/enhancing-repository-level-code-completion-with-selective-retrieval#:~:text=its%20outputs,it%20always%20the%20best%20choice) and learned filtering of retrieved results to prune irrelevancy [oai_citation:81‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=cross,retrieved%20contexts%20in%20code%20completion) [oai_citation:82‡openreview.net](https://openreview.net/forum?id=0Y2zXLFBji#:~:text=demonstrates%20that%20CODEFILTER%20consistently%20improves,while%20exhibiting%20strong%20generalizability%20across).
- *Structure-based selection:* Utilizing the code’s structure (ASTs, import graphs) to chunk and select context. By keeping functions/classes intact and providing scope metadata, we give the model more coherent and information-rich context [oai_citation:83‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=2) [oai_citation:84‡github.com](https://github.com/supermemoryai/code-chunk#:~:text=4). Dependency analysis brings in exactly the definitions needed for a piece of code.
- *Graph and knowledge-based context:* Building a knowledge graph of the code enables extremely targeted retrieval of the *connected pieces* of a codebase relevant to a query [oai_citation:85‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=generation%20with%20LLMs,accurate%20and%20contextually%20aware%20code). This method preserves relationships and can guide the model to produce consistent, integrated code [oai_citation:86‡arxiv.org](https://arxiv.org/html/2505.14394v1#:~:text=to%20information%20retrieval%20on%20code,existing%20code%20to%20minimize%20duplication).
- *Recursive/agentic approaches:* Allowing the model to manage context in an iterative way, as seen in Recursive Language Models, lets essentially unbounded exploration of an input [oai_citation:87‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=We%20introduce%20Recursive%20Language%20Models,LLM%20can%20symbolically%20interact%20with). The model can zoom in and out of parts of the prompt, summarize sections, and assemble an answer from partial results – dramatically extending effective context length without architectural changes [oai_citation:88‡arxiv.org](https://arxiv.org/abs/2512.24601#:~:text=,scaffolds%20across%20four%20diverse%20long) [oai_citation:89‡ar5iv.labs.arxiv.org](https://ar5iv.labs.arxiv.org/html/2512.24601v1#:~:text=find%20that%20RLMs%20successfully%20handle,cost%20per%20query).
- *Content addressing and novel compression:* Drawing inspiration from systems like Unison where code is identified by hashes [oai_citation:90‡renato.athaydes.com](https://renato.athaydes.com/posts/unison-revolution.html#:~:text=In%20their%20words%2C%20here%20it,is), we can imagine LLMs that reference code by ID rather than value, avoid duplicate inclusion of the same snippet, and fetch details only when needed. Other forward-looking ideas include providing interfaces over implementations and using learned compressions of text.

It’s likely that a *fusion of these strategies* will yield the best results. For example, an advanced coding assistant might maintain a graph index of the codebase, use it to retrieve a candidate subgraph for a query, chunk those code pieces with AST boundaries, rank them by relevance, and feed the top ones to the LLM. If the query is still too broad, the assistant could recursively break it down (à la RLM), perhaps even assigning subtasks to specialized agents (one agent handles retrieval, another handles summarizing a large function, etc.). Throughout, it might use content-addressable references to avoid repetition and keep track of what’s already known in the conversation.

What’s clear is that **context optimization is crucial for accuracy** – irrelevant or excessive context can confuse the model, while missing context leads to incorrect answers. It’s equally crucial for **cost and latency** – prompts that are half the length run twice as fast and cost half as much, which matters for real-time usage. As codebases grow and we expect assistants to handle entire repositories or extensive documentation, these context-engineering techniques become the linchpin that makes it feasible.

In conclusion, context engineering for coding agents is an active and exciting field. By intelligently compacting, selecting, structuring, and managing the information fed to code LLMs, we can greatly amplify their capabilities. The combination of retrieval techniques, program analysis, and even letting the LLMs themselves act as navigators of context (RLM) points toward a future where coding assistants can truly understand and work with projects of any size, all while staying efficient and focused. The lessons from these strategies will not only make Codex-like models better, but also help align AI assistance with the way developers think about and manage code – focusing on the relevant pieces while not losing the forest for the trees.
